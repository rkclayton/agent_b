# Agent_b v1.18.0

## Agent_b from a prompt

There is a second way to run it now:

    agentb "add a unit test for the parser and run it"

It runs one task in the current directory and streams to the terminal — one line
per tool call, the reply at the end, and why it stopped. It is the same engine as
the app: the same configuration, the same connections and credentials, the same
tools and the same folder rules. Approvals are terminal prompts carrying the same
two cards and the same scopes you see in the window.

    --json          the event stream, for scripts
    --unattended    nothing asks; hitting a boundary fails the run
    --profile       which connection to use, for this run only
    --continue      follow up in this folder's last session
    --memory        allow the run to write the memory layers

The run is recorded in the folder's own `.agentb/` in the same format the app
reads, so `agentb --replay` and the app see one file rather than two formats.
Without `--memory` the memory layers are read-only, because a one-shot task in
somebody's repository should not quietly change what the agent remembers
everywhere else.

It links about half of what the app does, and a test enforces that rather than
hoping for it: no web server, no window, no reflection, no updater, no signing,
no notifications.

**Not on the installer yet.** Build it with `go build ./cmd/agentb`; putting a
second signed executable in the installer changes what the release's signature
check counts, and that deserves its own pass.

## Diagnostic telemetry, and a switch that means it

Settings → About has a new switch: **Send diagnostic telemetry**, on by default.

What it sends is counts, durations, error classes and stop reasons — how long a
run took, which bucket the time went to, how many retries, whether a tool
failed and what kind of failure it was. What it never sends is anything about
your work: no message text, no model output, no tool arguments or output, no file
names, paths, hostnames, URLs or email addresses, no chat titles, no plan text,
no memory notes. Not "very little" — none. The list of what may leave is written
down in `docs/TELEMETRY.md`, and a test fails the build if Agent_b grows a new
kind of event that nobody has classified as either sendable or dropped.

**Off means off**, and it is not a filter. With the switch off there is no
collector attached at all, the queue on disk is deleted, and the sender is not
running. Turning it back on issues a new install id, which cannot be joined to
the old one. About also lists the last twenty batches exactly as they left the
machine, so you can check the paragraph above rather than take it on trust.

**Nothing is sent until you configure a receiver.** There is no default
endpoint: Agent_b does not know where yours is, and guessing would send your
counts to a stranger. Until one is set, nothing is collected and nothing is
queued.

The receiver is a small service you run — not something Agent_b installs on your
machine.

## Where the work lives

A new `docs/REPOSITORIES.md` says which of four repositories a piece of work
belongs to: the VPS (the broker, the telemetry receiver, and serving releases),
this one (the Windows harness and its installer), the Mac client, and Android
when it starts. It also says plainly what the VPS cannot do — it cannot build a
signed Apple client, because that needs macOS — rather than leaving it to be
discovered.

## What we measured and did not change

Two things were measured this release and deliberately left alone.

**Reflection** — the pass that summarises a finished run — costs one model call
per run. Over the recorded history that is 17% more model calls overall, but the
distribution is the real finding: most runs are short, and for a run that made
one model call, reflection doubles it. Four things read its output, so it is
worth keeping; a floor, so it only summarises runs that did enough to be worth
summarising, would cut the overhead to about 5%. Not changed yet.

**The stuck-run detectors** were replayed over every recorded run. Four of the
six have never fired at all; the two that do fired five times, always on runs
that finished cleanly. None of them is armed, and none of them should be armed on
that evidence — but the honest conclusion is that there is not yet enough history
to set their thresholds from, and saying so is more useful than a number with
nothing behind it.

## Smaller things

Every tool failure now carries an error class from a fixed list, so a failure can
be counted and compared instead of only read.

A run's stop record now says whether the model was local or remote — the class,
never the endpoint or the model's name.

The connection-replay gate used to need somebody to stage a build for it first.
It builds its own now and cleans up after itself, so it runs from nothing.
