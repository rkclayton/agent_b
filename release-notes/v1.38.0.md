# Agent_b v1.38.0

## Added

- A service you already use can now tell Agent_b what it offers. Ask in a chat to add a connector and point it at the service's own published description; Agent_b reads it once and asks you to approve, on the same card connectors have always used. The card lists exactly the operations it would enable — each one's name, what it does and what it takes — so you approve a list you can read rather than an address.
- After that the model calls those operations by name, with named values, instead of being told an address and a method in prose. It cannot reach anything else on that service: the description you approved is the list, and a call to some other path is refused with the operations it does have.
- Values are checked before anything is sent. A missing one, a name the service does not know, a number where text was given, or a choice outside the set the service allows, each come back naming what was wrong, and the service is never called.
- Nothing about the service's key changes. The credential stays the one you configured, on the host you configured, and is never taken from the description.

## Under the hood

- The approved description is kept beside the connection credentials and pinned by its digest. If that file is ever changed afterwards, the connector's operations are refused until it is imported again — an edited description is one nobody approved.
- The list the model is given is rebuilt from the configured connectors on every request, so a connector approved mid-chat is usable on the next turn. No tool was added, and the tools Agent_b already had are exactly as they were.
- The whole path is checked by tests against a made-up service and its description, and was then run end to end in one chat on a throwaway copy: the proposal, the card, approval, one real call, one refused call to another path, and one refused value.
