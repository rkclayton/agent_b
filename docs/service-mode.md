The Windows service and the tool service identity do cross at child-process logon, file impersonation, and access to the stored tool-account password; they remain two separate identities with different jobs.

# Before-sign-in service: proposal, not an implementation

Read against `f10e107`, 2026-11-16. A boot-time server is feasible, but the current executable cannot simply be registered as a service. No service, task, account, configuration, installed copy or credential was changed or exercised for this report. Console: not elevated. Platform references below were consulted on 2026-11-16; “works” describes the code's dependency, not a completed service test.

## 1. How it starts now

The hidden launcher starts the per-user executable with explicit application/data/config roots (`scripts/launch-Agent_b.ps1:364`). The native installer chooses per-user application, data and workspace roots (`cmd/harness/install_native_windows.go:29`). The About sign-in switch writes the current user's Run entry, so it starts after sign-in, not at boot (`internal/web/server_actions.go:416`, `internal/web/folder_windows.go:33`).

Before normal initialization, a window launch tries `activateExistingInstance` (`cmd/harness/startup_launch.go:114`). That reads `agent_b-run.json`, checks application root, PID and creation time, verifies the loopback server's reported PID, then signals its activation event (`cmd/harness/lifetime_windows.go:113`). Success logs “activated existing PID” and exits without another server. The run marker and launcher log live under the data root (`cmd/harness/lifetime.go:74`). A background launch still prepares a host bridge so a later launch can open its window (`cmd/harness/startup_config.go:73`, `cmd/harness/main.go:736`). This is an existing-process activation path, not a cross-session singleton lock.

## 3. Which account

Recommend the **operator's own account for the first service design**, because it preserves existing DPAPI identity, data ownership and chats without migrating secrets. This recommendation is conditional on preserving the app's non-administrator execution posture. The current effective-admin check refuses startup (`cmd/harness/elevation_windows.go:9`, `cmd/harness/main.go:540`); do not bypass it to run an administrator service. A prototype must prove a suitably restricted runtime token under SCM, or this account choice is not viable. That token arrangement and DPAPI access are **not determinable without elevation**. The service must never turn user-writable configuration or commands into administrator execution.

SCM loads the service account's profile and stores its logon credential through Windows, not application configuration. A password is retained as an LSA secret; password expiry/change without updating the service credential prevents a subsequent start. A PIN is not a substitute in this proposed password-based setup. Show a repair action for changed credentials, without logging them. [Service User Accounts](https://learn.microsoft.com/en-us/windows/win32/services/service-user-accounts), updated 2021-01-07; [logon types](https://learn.microsoft.com/en-us/windows-server/identity/securing-privileged-access/reference-tools-logon-types), updated 2024-05-30.

A different account has a different DPAPI identity and cannot simply decrypt the existing keys. The restricted tool account is particularly unsuitable as the app account: its data-root access is traversal only, with selected plan/scratch/chat/workspace/exchange grants; configuration, credentials, retained journals, logs and memory are outside that access (`SECURITY.md:21,126,300`). A fresh dedicated app account would need explicit data ACL and secret migration, separate from the tool account. LocalSystem is not the recommendation: besides excessive authority, it is incompatible with the current tool-process logon API (below).

## 5. Attaching the window after sign-in

Read this one: `cmd/harness/lifetime_windows.go:113`. Both activation and stop events use `Local` names. Microsoft's [kernel-object namespaces](https://learn.microsoft.com/en-us/windows/win32/termserv/kernel-object-namespaces) distinguishes session-local from global names; a desktop process will not signal the service's local event. Even a shared event would ask the service to open a window in the wrong session.

The desktop launch should instead verify the service PID/start identity and open a client-only host against its authenticated loopback endpoint, with an ACL-bound IPC channel for desktop actions. Keep local operator authentication and phone restrictions intact. Add one cross-session ownership lock per canonical data root before any writer opens stores. Today a failed activation falls through to ordinary startup; a duplicate bind may reject the second server, but that is not a data ownership guarantee. Two accepted writers on different ports could overwrite configuration, race journals/markers and duplicate jobs. Refuse a second data owner; never silently create a fresh profile to mask failed attachment.

## 6. Smallest proposed change set and one-time request

1. Add an explicit SCM entry/lifecycle adapter to this binary; resolve configured roots independently of a desktop environment. Start the headless server, report status, stop cleanly, close model jobs and journals. Retain the normal-launch elevation refusal. First prove the restricted runtime token/profile arrangement described above.
2. Add a client-only window mode and authenticated service/client attachment. Move notifications, pickers, file opens, OAuth consent and setup prompts into that client. Prevent duplicate writers across sessions.
3. Extend the installer with an opt-in service registration helper. One elevated setup action shows the account, application/data roots, automatic boot start, service logon right and exact rollback; obtains the account password through a protected Windows credential UI; passes it directly to SCM; never stores it in app configuration. It verifies readiness before reporting success. Service installation/access rights are administered by Windows ([service security](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights)). A failed setup rolls back only its own new registration/rights and preserves data.
4. About's current **Start when I sign in** becomes **Start before sign-in** for service mode and reflects SCM's configured startup state. Opening the window at sign-in remains a distinct client preference; do not have its old Run entry launch another server. Disabling boot start does not delete chats or silently kill a current run.
5. Update through SCM: suppress automatic restart while replacing, request stop, retain 2y5's 15-second grace and verified PID/creation/image handle before any authorized force; confirm exit before replacement, then start the verified signed build and prove readiness. Never kill by process name. Uninstall removes this service/registration and its client startup entry, not shared tool-account controls or retained data. Machine-wide changes need the installer helper; they cannot be assumed to fit today's unelevated updater.
6. In one disposable Windows service test installation, prove boot-before-login and logout survival; DPAPI reads/token refresh with dummy secrets; non-admin runtime; single writer and client attachment; denied foreign client; idle/model cleanup; crash/recovery; password-change failure/repair; update with stale/PID-reused markers and held streams; uninstall preserving data; and the full tool-identity ON/OFF matrix. Test headless Edge and the actual approved GPU backend separately within that installation. An initial elevation can install the fixture, but reboot and password-change cases require additional phases, not a fictitious single invocation.

What would be asked once for normal setup: choose service mode, confirm the account and protected credential, and approve the shown Windows service installation. Password rotation or future machine-level maintenance may require another credential/elevation; “once” is not a promise that Windows will never ask again. No such request is made by this research block.

**Not determinable without elevation:** actual SCM restricted-token/profile startup; existing-user DPAPI and certificate-provider access before login; named-parent tool process/job/impersonation behavior; real browser startup; phone reconnect before login; GPU backend support; service update/uninstall/recovery. The disposable installation above settles these without using production data. This proposal is committed documentation only; there is no service release or service-runtime proof.
