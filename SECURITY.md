# Security

Agent_b executes shell commands selected by a model. Use it only where that authority is acceptable.

## Workspace and shell boundary

A B-role session's application guard is a union: its own scratch or retained legacy root plus the canonical repository of every registered plan. Relative paths resolve from the session root; absolute paths select the longest matching registered repository; paths outside the union retain the established refusal. Plan files under `<data-root>/plans` are readable by every B and D session but writable only by the D session bound to that plan; the internal `plan.json` repository manifest is model-immutable because it defines the union. A D-role session otherwise has the stricter application guard: writes stay in its immutable plan folder, repository access is read-only, and D cannot enable `shell` or `run_script`. D paths are canonicalized after root selection so repository or plan-tree symlinks cannot escape this rule. Operator identity and per-chat file grants do not disable the plan-write rule, and write_file and edit_file compare a target with the plans folder both as written and as the file system resolves it, so a junction, symbolic link or reparse point in a chat folder cannot reach plan files under another name (item 2fq). Since v0.70.0 the folder guard itself judges both the folder and the target by the path the file system resolves (the final path by handle), so a junction inside a chat folder or a registered repository that leads elsewhere is outside the folder. Registration stores the resolved folder, so a link re-pointed after registration changes nothing, and it refuses the operator's connection folder itself and anything in the Windows or Program Files folders, wherever the typed path led. A repository policy's `default_toolset` never turns `shell` or `run_script` on for a D session. The plan list is therefore the file-tool allow-list, but all of these guards are routing ergonomics layered inside the OS boundary—not containment and not a replacement for the service account and ACLs.

The hardened ACL policy makes the minimum matching OS exceptions: the service account may traverse the operator data root but may not list, read, or mutate it, while the `plans` and `scratch` children have explicit recursive `Modify`. Existing hardened installs must reapply Host protections before relying on D writes or scratch chats; that operator-only action is never performed by an application upgrade. Configuration, credentials, logs, retained chats, and memory remain outside service-account reach.

With the service identity disabled, the root union remains the boundary for built-in file tools solely because `internal/tools/jail.go` constrains their paths; that guard is not a security boundary and must not be removed. In that posture an outside-union path is not simply refused (item 2fi): the file tools, and a `shell` command or `run_script` source that names a literal absolute path outside the union, raise the same **Run as you** decision the service posture raises, and hold until the operator answers; approval reruns that exact call once as the operator, a decline leaves the refusal as the result. The card's text names every outside path it found (up to twelve, then a count), and a `run_script` card carries the script's source. **Yes, for this chat** in this posture lets that chat's later outside-folder calls run without asking until the chat closes; it stores no identity grant, so turning the service identity on later does not wake a grant the operator gave in the other posture. The literal-path scan cleans a path before comparing it, so `<folder>\..` is outside; only a path to an `.exe` that exists as a file is exempt, and `.cmd`/`.bat` text is not. Root-relative (`\Windows\…`), drive-relative (`C:Windows`), relative climbs (`..\..\`), environment-variable and `~` forms, and encoded commands are not seen. This widens what is reachable to what the operator approves case by case. The card is the boundary's ergonomics, not its enforcement: a path assembled at runtime, or any interpreter code that reads a file without naming it literally, is not seen, and nothing here is a sandbox. With the service identity enabled, those file operations impersonate the configured low-privilege Windows account after root selection, and Windows ACLs remain authoritative over the selected target. The `shell` tool is not jailed and never has been: the session root is only its initial working directory, and it can change directories, use absolute paths, invoke network clients, and run any program available to its active token. Service-account ACLs constrain what shell can reach, not what it can do with reachable resources. The wrapper kills the process tree on timeout, checks a small configurable denylist, and logs the complete call and result. [Windows host hardening](docs/HARDENING.md) reduces blast radius; it is not an OS sandbox.

**Existence of an outside path (item 2fy, v0.71.0).** A file tool's target outside the folder that does not exist raises no card: the tool answers "no such file or directory … it is outside the folder". Existence is judged in the identity the tool runs as. Under the service account that is the account's own view — a path it cannot see answers "denied" and still raises the card. **With the service identity disabled it is the harness's view, the operator's: a model can now learn, without the operator seeing a card, whether any path the operator can traverse exists** (it learns nothing of its content). Before v0.71.0 every outside path raised the same card. This is accepted by 2fy's contract and recorded here; the service identity removes it.

**Reflection reads what the model read (item 17-i, v1.1.0).** Reflection's summary is written by the model from a transcript that can contain text the operator did not write — a fetched page, a search snippet, a file's contents, a tool result. That summary is stored, shown on Console, and can produce a memory note, which is durable prompt material for every later run in that folder. So: a run that used `fetch_url`, `web_search`, or `call_service`, or whose result the tool layer marked untrusted, produces **no** memory note at all; every note reflection does write is prefixed `[reflection, unconfirmed]` so a reader knows nobody confirmed it; a pass writes at most six; and each is published as `memory.noted`, so dropping a chat's memory drops these too. Reflection registers no plan: it names candidate repositories in its overview text and the operator registers them through the existing card. The structure extractor runs a repository's own toolchain, so its environment is pinned (`GOTOOLCHAIN=local`, `GOPROXY=off`, `GOFLAGS=-mod=readonly`, `GOWORK=off`, `GOBIN=`; `CARGO_NET_OFFLINE=true`, `RUSTUP_TOOLCHAIN=`, `RUSTC=`) rather than inherited, so a hostile `go.mod` or `rust-toolchain.toml` cannot choose the binary that runs; files over 1 MiB are not read, and at most 4,000 are walked.

**The shell's interpreter (item 2gb, v1.0.1).** The shell tool and `run_script powershell` run PowerShell 7 when it is installed machine-wide (`%ProgramFiles%\PowerShell\7\pwsh.exe`, or the ProgramW6432 and 32-bit equivalents), and otherwise the configured Windows PowerShell. The interpreter is never taken from `PATH` or from a per-user location such as `%LOCALAPPDATA%\Microsoft\WindowsApps`: anything a non-admin can write there would become the process every shell call runs, including the calls that run as the operator. On a 5.1 host the model's top-level `&&` and `||` are rewritten before execution; the rewrite never touches quoted text, here-strings, comments, or anything after `--%`, and a command whose quotes or brackets do not balance is passed through untouched. The deny list, the routing guard and the operator-identity checks all read the model's original text, and the rewritten command is written to the operator's log whenever it differs.

**Directory changes and listings (item 2fz, v1.0.0).** With the service identity disabled, the shell's and `run_script`'s literal-path scan now classifies each outside path by the statement it sits in: the argument of a directory change or listing (`cd`, `pushd`, `Set-Location`, `dir`, `Get-ChildItem`, `tree` and their aliases) raises no card, unless a file-reading verb or form (`type`, `Get-Content`, `copy`, `Select-String`, `certutil`, `robocopy`, archivers, `Invoke-Expression`, a subshell, an opener or uploader, any `[IO.*]` class, `<`, …) appears in that statement's arguments or later in the same source, in which case the change counts as a read. Statements split at `&&`, `||`, `;`, `|`, `&` and line breaks; the v1.0.0/W4 cold review found `cd /d C:\ & type <outside file>` read with no card when cmd's bare `&` did not split, and relative reads after a `cd` through `certutil`, `robocopy` or `[IO.StreamReader]`; both are fixed. Any other outside path is treated as a read: the card when it exists, a plain "no such file or directory outside the folder" error when it does not — the same existence oracle as 2fy's, now for the shell too. What this widens, without a card: listing the names in any folder the operator can traverse, and running a program (not a named read verb) from an outside folder as the working directory — a program so run can read relative files the scan never sees. The classifier is a first-token heuristic, not a parser; it was already true that a path built at runtime is not seen, and this is ergonomics, not containment.

The default file-routing guard refuses simple shell shapes that duplicate `find_files` or `read_file`. It is a routing aid, not a security boundary: it does not restrict what the shell can do and is not a sandbox. `tools.find_files.skip_roots` avoids recursively enumerating known protected Windows and Defender trees under either identity; it is behavioral hygiene, not access control, and Windows ACLs remain authoritative.

The install-global Docker Sandbox switch defaults on. When `sbx` is ready, `shell` and `run_script bash` use a sandbox whose host mounts are the session scratch/retained root plus only registered plan repositories selected by file operations in that run. Docker's local daemon and OAuth authentication are bound to the operator's OS-user session, so these calls run under the operator's Docker session, not `agentb-svc`, and are outside the service account's SID-scoped firewall rule. Agent_b raises the existing **Run as you** identity decision before such execution. The microVM is the sandbox boundary; every supplied host mount is deliberately read-write. An absent or signed-out `sbx` leaves the switch on but inert and exposes the reason; ordinary shell falls back to its normal host identity, while `run_script bash` refuses because it has no host fallback.

Agent_b never launches PowerShell with an execution-policy bypass and rejects a model command that proposes one before creating a process. Shell rejects commands that write Windows script-host artifacts and refuses to execute an agent-written `.ps1`/`.psm1`/`.bat`/`.cmd`/`.vbs`/`.wsf`/`.hta` through PowerShell, pwsh, cmd, wscript, cscript, or mshta. Python, Node, Go, .NET, and other interpreters are deliberately outside that narrow provenance rule. Multi-line PowerShell uses `run_script`, which passes source on stdin with `-NoProfile -NonInteractive -Command -` and never uses `-File` or `-EncodedCommand`. These are process-tree hygiene controls, not containment; a shell remains capable within the permissions of its active Windows token.

Code-signing commands (`Set-AuthenticodeSignature`, `signtool`, and `certutil` store operations) are blocked from `shell` and `run_script` under every identity. Signing is available only through Settings and is guarded by the verified operator HTTP-process check. Create uses UAC to place a non-exportable key in `LocalMachine\My`; its default machine-key ACL limits private-key use to elevated administrators/SYSTEM, while only its public certificate is trusted in the operator's CurrentUser TrustedPublisher and Root stores. This makes upgrades silent inside the already-elevated installer without giving non-elevated operator mode or `agentb-svc` the signing key. Import places a code-signing-EKU certificate in `CurrentUser\My`, uses the PFX password once, does not alter trust stores, and does not add Windows strong key protection. Before any signing path opens a private key, it queries the CNG UI policy with the silent flag and refuses a key that could display interactive private-key UI; a non-elevated LocalMachine key remains an allowed elevation-gated result and still fails closed until the existing elevated path runs. The elevated signing helper accepts no filesystem paths, derives roots from the verified running process, compares the executable SHA-256 shown by `/api/state`, stages and verifies signatures before replacement, and restarts with the operator's limited token. `signing.applied` is the durable audit record after restart.

Developer acceptance uses a separate `CN=Agent_b Disposable Test Signing` identity, never the production identity. `scripts/new-test-signing-certificate.ps1` is an explicit operator-run bootstrap with `-WhatIf` support: it creates a one-year, non-exportable CurrentUser key with interactive key protection disabled, proves the private key can sign before adding trust, and trusts only its public certificate in that same user's Root and TrustedPublisher stores. This deliberately lets that Windows user trust test executables signed by the key; compromise of the user account can therefore produce locally trusted test signatures. The key is neither reachable by `agentb-svc` nor portable to another host, and executable acceptance selects this exact subject. Removing the three exact CurrentUser certificate-store entries revokes the test identity.

The non-elevated-operator side of that signing boundary was checked directly on 2026-09-06: a medium-integrity Explorer-token child could not sign with LocalMachine certificate `8C7AB22A989F6B99B867868A52920119C3EDFFEB` (`result=DENIED`), as recorded in `%LocalAppData%\Agent_b\logs\main-20260906T123516.jsonl` and `NOTES.md`.

Model-connection API keys are not stored in `harness.json`. A connection keeps a lowercase credential reference; the corresponding value is protected with Windows DPAPI under the launching user's scope and decrypted into the in-memory connection when configuration loads. Masked API responses and configuration events expose only `•••• set`, and request/event logs do not contain the key. The existing service-account password remains in its separate fixed DPAPI store.

The Discord webhook follows the same credential rule: `harness.json` contains only `notifications.discord_credential`, while the URL is user-scoped DPAPI data and is never returned by APIs or written to events. Notifications run in the non-elevated harness process as the operator, not as `agentb-svc`. Their dedicated client accepts only an HTTPS Discord webhook path on an exact supported Discord host, refuses redirects, disables mention parsing, and cancels delivery when that configured destination changes; removing the credential removes that in-memory destination. This is a narrow application egress guard, not containment, and it does not change the SID-scoped service-account firewall or the separate `fetch_url` policy.

The first-run wizard adds no persistent completion state and does not change probe semantics. Its local detector is read-only: it queries Windows hardware/process information and known executable locations and does not alter `PATH`, install software, download models, or start connections. The separate operator-selected **Install one here** action does download and start a model stack: the browser can submit only compile-time catalog IDs; URLs, exact byte counts, SHA-256 values, and backend archives come from the server's pinned catalog. Production downloads require HTTPS, reject HTTPS-to-HTTP redirects, stream into `.part` files under the data root with an exact `bytes+1` ceiling, and are renamed only after byte-count and SHA-256 verification. Runtime zip extraction follows verification, rejects traversal and links, caps total declared expansion at 2 GiB, checks each extracted length, and requires exactly one `llama-server.exe` before writing the sign-in launcher or starting anything. The server, not browser input, obtains the selected backend's available memory; after checksum verification it reads the GGUF context/KV metadata, refuses an 8192-token context that cannot fit weights plus f16 KV cache and the fixed reserve, and writes the derived explicit context into the launcher and connection. A malicious release host or DNS answer can deny service but cannot supply executable bytes that pass the pin; changing the browser recommendation table cannot change server-side artifacts or the memory used for context sizing. The installed server and GGUF deliberately run with the operator's authority, not `agentb-svc`; this is local model installation, not containment. An interpreter's `runs as service` label means the configured service account (or a broad built-in group it belongs to) has read/execute ACL entries on the resolved executable; `operator-only` means that check found no such grant. This display is an onboarding hint, not a security boundary or a proof that every dependency is reachable. Windows ACLs remain authoritative at execution time.

The Settings → Security control labeled **Run everything as me for 20 minutes** is an explicit, process-global capability escape hatch. It bypasses service-account isolation for shell and file tools, including the file tools' workspace boundary, and leaves access decisions to the non-elevated Windows account that launched Agent_b. Switching modes is immediate and does not open a confirmation dialog. While active, every Chat status strip shows `operator mode · until HH:MM`; Settings shows the high-contrast active robot glyph and both surfaces return to off state from authoritative server events when a grant fails or expires. Operator-mode transitions are status, not agent-authored chat messages. Each SSE connection and foreground resume reconciles server state so a suspended or disconnected client cannot retain a stale privilege indication when it resumes. Operator mode is always off after startup and process exit. It has no absolute ceiling while active work continues: by default it turns off after 20 minutes without ordinary agent tool execution, and every such execution resets the deadline at start and completion. Browser/SSE/config reads and the one-shot ACL escape do not reset it. A single tool call running longer than the window is deliberately allowed to lapse rather than risk an indefinitely open grant behind a wedged call. Every transition, reset, and operator-context tool result is logged. Enabling, disabling, or changing the service-identity configuration through HTTP requires the request's local client process to belong to the Agent_b operator and rejects Agent_b itself or any descendant process; possession of the browser mutation token alone is insufficient, so neither a service-account shell nor an operator-context shell can change the mode or disable the split. This does not grant Administrator authority, bypass Windows ACLs, or create a sandbox.

In service-identity and operator-context modes, B-role built-in file tools deliberately let Windows ACLs authorize paths and do not pre-resolve symlinks or open every ancestor for metadata inspection. This widened resolution at `ce73fc0`: ACL-authorized targets beneath traversable but metadata-inaccessible parent directories, and OS-authorized symlink paths, can now reach the underlying file operation where previously the metadata check could reject them first. The ordinary workspace-bound mode still canonicalizes symlinks and rejects escapes; in OS-authorized B modes the Windows token is the intended boundary. D always canonicalizes because its plan-write restriction is immutable under every identity.

When `shell.service_account.enabled` is false, the shell inherits the Agent_b process identity and environment as before. When it is true and the stored credential works, Agent_b creates shell processes under the configured low-privilege Windows identity with an explicit minimal environment. Its `PATH` contains only Windows system directories and the Windows PowerShell directory, so other tools require absolute paths. A failed alternate-identity launch does not execute the command: it logs the reason, raises persistent red status text in the header, and requires the user to approve an exact-command operator retry. The alternate path preserves the initial working directory, combined output, timeout, and process-tree termination through a Windows job object, but it still requires an operator-machine test before being relied upon. A separate account limits reach; it is not a sandbox and does not contain an exploit. Follow [Windows host hardening](docs/HARDENING.md) before relying on the split.

Office files (item 2ep) add no dependency: `.xlsx`/`.docx` ingest and `.xlsx` output use only the Go standard library (`archive/zip`, `encoding/xml`, which never resolves external entities), within the attachment byte bound. Written workbook cells are inline strings or numbers, never formulas. The Chat delivery chip's open action runs in the harness process as the operator and opens only document types, because a default open of a script or executable would run it.

PDF attachments (item 2fj) add one dependency, `github.com/ledongthuc/pdf` (BSD-3-Clause, pure Go, no cgo, no dependencies of its own), which reads a PDF's text layer locally when the connection has no document input and no extraction service is configured. It parses untrusted input: its panics are recovered and reported as an unreadable PDF, never allowed to reach the server, and a file missing its cross-reference table is repaired in memory only. A PDF with no text layer is rendered page by page by the Windows inbox PDF renderer (`Windows.Data.Pdf`) and read by the same inbox OCR as images, at most 20 pages. Both sidecars are framed as untrusted evidence, like the extraction service's.

Dependency alerts (item 2fr) are sorted by whether the code ships. A runtime alert — a module compiled into `Agent_b.exe` whose vulnerable code the binary reaches (`govulncheck`) — is fixed in the next release by upgrading within the Go language version the repository builds with; one whose fix needs a newer Go stays open with that reason until the toolchain moves. An alert on code the binary never compiles or calls is dismissed with that reason. Node packages are test tooling and ship in no artifact; their alerts are triaged. As of v0.70.1: `golang.org/x/net` v0.50.0 and `golang.org/x/crypto` v0.48.0 (the newest on Go 1.24); five `golang.org/x/net/html` advisories reachable through `fetch_url`'s text extraction remain open because their fix (v0.55.0) requires Go 1.25, and `fetch_url` bounds the body it parses to its byte limit; the `golang.org/x/crypto` SSH advisories are not compiled in (the binary uses only `chacha20poly1305`, through `utls`). `x/net` v0.50 refuses HTML nested more than 512 elements deep; `fetch_url` then returns the page's text with its tags removed and a line saying why, never nothing.

Service-account processes are started on the operator's interactive desktop, so since v0.65.0 their job object carries UI restrictions set before the process runs: they cannot use USER handles owned by processes outside the job (another process's windows, including Agent_b's own hidden session window and the operator's applications), create or switch desktops, change display settings or system parameters, read or write the clipboard, use global atoms (DDE), or call `ExitWindows`. A tool process can still see that such a window exists; it cannot post or send it messages. **This is not isolation from the desktop.** The processes still run on the operator's interactive desktop, and the job limits do not stop synthesized input (`SendInput`) or global window hooks; only a separate desktop for service-account processes would, and that is a pending operator decision (v0.65.0 card). Until then, the service account's reach over the operator's open windows through input injection is an accepted, documented gap. Agent_b's hidden session window additionally ignores `WM_CLOSE` and records a session end only when Windows sends `WM_QUERYENDSESSION` and then `WM_ENDSESSION`, never for a posted message. The installer's graceful stop uses an install-root-and-process scoped named event (`Local\Agent_b-stop-<canonical-root-sha256-prefix>-<pid>`) whose DACL admits only the operator's account and SYSTEM; a process that finds the name already taken does not use it. The root digest is addressing, not an authentication secret: it prevents an installer operating on one application root from naming another root's channel, while the DACL remains the access boundary. Only the installer, after exact executable-path selection, may use the unscoped earlier-version fallback during an upgrade. A live probe on a disposable install (`scripts/test-window-probe.ps1`) runs as a service-account tool process and proves both messages and the event are refused. These restrictions do not cover operator-identity processes (Run as you, operator mode, the page itself), which can still address the operator's own windows.

On Windows, the normal service-context process tree is `Agent_b.exe → powershell.exe → any program named by the inline command`. `CreateProcessWithLogonW` creates PowerShell directly as the service identity; there is no intermediate `cmd.exe` or generated script. `fetch_url` performs anonymous, governed open-web HTTP inside `Agent_b.exe`; it neither downloads through PowerShell nor hands fetched bytes to the service shell. `call_service` is deliberately separate: it reaches only configured internal-service base URLs, attaches only the configured service identity, and runs an `exec:` credential argv directly as the non-elevated operator with no shell. Its bearer value remains in process memory, model-supplied authorization values are redacted from durable/UI projections, and any reflected token is scrubbed from the returned body. A configured service is an explicit authority grant, not an extension of the public-web fetch policy.

Settings can launch the account setup script as a hidden elevated helper through Windows UAC while Agent_b remains non-elevated. The two password entries are write-only, are never placed on a command line or in logs, and cross the elevation boundary only as the existing user-scoped DPAPI blob. Keep the service on loopback, approve UAC only for an operation you initiated, and treat any failure after the elevated helper starts as a potentially partial account/password change.

Agent_b refuses to start when its effective Windows token is elevated, before loading configuration, probing a model, opening the listener, or enabling shell execution. Membership in the local Administrators group is allowed: a normal Explorer launch uses the UAC-filtered token. This keeps **Run once as operator** from inheriting Administrator authority.

The model prompt receives only OS-derived date, timezone, and (on Windows) a coarse region code. Agent_b does not collect precise device location or infer a city from that context; this information is convenience context, not a location-tracking feature.

Settings can also apply and verify complete-tree service-account ACLs and an account-scoped outbound Block rule through UAC. The ACL policy grants mutation to data-root `plans` and `scratch`, the exchange folder, and a legacy workspace only when that compatibility root exists; it must be reapplied after application updates create or replace files. The default firewall policy permits loopback and the configured model server. A model hostname is resolved when protection is applied; the name-to-address mapping is recorded on the rule, and a later resolution change is reported as drift that requires re-application. Optional `shell.allowed_model_ranges` entries are explicit operator-owned IPv4 CIDR exceptions; there are no implicit VPN-product ranges. The policy does not change machine-wide firewall defaults or inspect destinations above the IP layer. **Allow my local network** is off by default. Enabling it is a deliberate widening of the OS boundary: the HTTP request must come from a verified local process owned by the server account or in the same interactive Windows session, the operator must confirm detected RFC1918 IPv4 subnets, Apply protection subtracts only those prefixes from the service identity's Block rule, and a SID-scoped outbound ICMPv4 echo rule is limited to the same prefixes. Disabling and applying restores the configured boundary and removes that echo rule. `fetch_url` follows the same confirmed-prefix decision while retaining DNS and redirect rechecks. Link-local addresses, `169.254.169.254`, and the Agent_b listener remain refused with the switch on. A device on an allowed LAN can therefore receive connections and malicious fetched content can reach LAN HTTP services; fetched bytes remain explicitly untrusted, and neither condition grants filesystem or operator identity.

Chat file downloads are read-only operations performed by the Agent_b server process as the non-elevated operator. They expose only regular files that the shared file-tool jail resolves beneath the selected session workspace; this jail remains an application guard, not containment. The open-folder action is mutation-token protected and resolves its selection through the same jail before asking the operator desktop to reveal it.

The exchange folder is a fourth, explicitly configured reachable tree, separate from application, operator data, and workspace roots. Host protection grants the service identity recursive `Modify` on that folder and only traverse access on otherwise private ancestors needed to reach it. This intentionally widens the OS boundary to the exchange folder so files placed there can later enter the attachment workflow; changing the folder requires reapplying and verifying host protection. Network shares, mapped drives, and SMB credentials are not supported.

Attachment ingest is an operator browser action protected by the launch mutation token, not a model tool or approval escape. The operator-context HTTP process writes at most `tools.attachments.max_bytes` beneath the selected session workspace's `attachments/` directory through the shared file-tool resolver; the service identity subsequently reads those bytes under the workspace ACL. Filenames are reduced to safe basenames, ZIP archives are refused, collisions never overwrite, and JSONL records contain only path, size, and SHA-256—not attachment bytes. Native document/image bytes exist only in the in-memory model request. Configured extraction endpoints receive the uploaded file and their text sidecars are explicitly labeled untrusted; Office XML extraction is bounded and uses the standard library without extracting archive paths.

Every native document/image content part is immediately preceded by a separate harness-generated text part that describes the following payload as untrusted evidence, never instructions. The framing describes the operator's attachment action without speaking as the operator. One frame governs one adjacent payload; base64 remains a non-text data URL and cannot forge the text delimiter. Before dispatch, encoded data-URL lengths are conservatively treated as an upper bound in context tokens and allocated cumulatively across retained attachment history against the connection's `n_ctx - reserve_output`; a payload that does not fit is not sent and receives an explicit outcome in both Chat and model-visible text.

Image OCR is local and uses the inbox Windows Runtime APIs in `combase.dll` and `shcore.dll`; it adds no helper process, packaged binary, language payload, or network destination. OCR sidecars remain inside the workspace, are labeled untrusted derived content, and state that layout was not preserved. The per-connection `native` override deliberately trusts the operator over a capability probe and may send document/image bytes to that connection's configured model endpoint; `extract` keeps those bytes local. This routing choice changes data handling, not the OS security boundary.

The Windows installer uses same-user UAC elevation to place immutable application files under `%ProgramFiles%\Agent_b`; it refuses elevation performed with another administrator identity so `%LocalAppData%` and user-scoped DPAPI cannot silently bind to the wrong connection. Configuration, credentials, logs, memory, plans, scratch chats, and detached-start diagnostics remain operator-owned under `%LocalAppData%\Agent_b`. Fresh installs do not create `%ProgramData%\Agent_b\workspace`; upgrades and retained chats preserve that legacy compatibility root when it exists. The non-elevated child writes its own per-launch startup diagnostic; the elevated installer does not capture or gain access to a new secret. An unsigned Agent_b binary in a user-writable AppData installation was quarantined once as a behavioral detection. Program Files is therefore required both to remove that risk factor and to prevent the constrained service identity from modifying the binary that constrains it; no Defender exclusion is requested. Signing is an install-time step: the non-elevated release step leaves the staged candidate unsigned by design, because the signing key in `LocalMachine\My` opens only elevated, and the elevated installer signs `Agent_b.exe` and every installed PowerShell script with the configured certificate (transcript line `SIGNED:`). The installer never builds: it installs only the exe named by the candidate's `candidate-final.json` (SHA-256 and the tag and commit embedded in its Go build information), checked before anything is stopped and again after. The manifest sits in the same candidate directory as the exe and the installer scripts that run elevated, so the check catches a wrong or stale exe, not an attacker who can write the candidate directory (who already controls what the elevated installer runs); that directory must be operator-controlled. The manifest binds the exe only, not `web/`, `scripts/` or `prompts/`. The uninstaller can preserve or purge the data root and optional legacy workspace, but it does not silently delete the service account, ACL policy, or firewall rule because those machine-level controls may be shared.

## Approval and unattended runs

Agent_b has two user-facing prompts. **Allow this** governs a risky action under `approval.mode` or a trusted repository policy: the shipped `boundary-only` default runs tools without generic pre-execution confirmation, `mutating` pauses `write_file`, `edit_file`, `shell`, and `run_script`, and `all` pauses every tool call. **Run as you** governs every need for the operator's Windows identity: configured operator commands, built-in file operations outside the service account's reach, and operator-only interpreters. Its buttons are **Yes, for this chat**, **Just once**, and **No**. One chat grant covers all those identity needs until `session.closed` or explicit revocation; it is durable, never global, and is not a separate shell/file permission. The Settings operator mode is the distinct process-global control and is never implied by a chat grant. If the service identity is disabled, there is no identity gate because the operator is already driving an unrestricted shell. Approval reduces accidental actions; it does not turn the shell wrapper into a sandbox.

**Unattended (item 5f, v1.2.5).** The Settings → Security switch **Unattended: never ask; boundary hits fail the item** changes WHO IS ASKED and nothing else. It narrows nothing about identity: tools still run as whoever they would have run as, and the boundary still refuses exactly what it refused before. With it on, a worker or scheduled run that would have raised any of the four cards — a policy approval, an identity escalation, a cycle decision, or a plan registration — instead records `[!] boundary: <what>` on its item and carries on, and the report lists every hit. A chat the operator is typing in stays attended regardless, because he is there and asking him is the point. Unattended and operator mode are independent: both on at once is a deliberate choice made in Settings, never one arrived at by accident.

When Windows denies a built-in file operation, shell output looks like an OS permission denial, or a requested interpreter exists only for the operator, Agent_b raises **Run as you** in every approval mode. **Just once** reruns only the displayed operation; **Yes, for this chat** sends later file, shell, and interpreter identity needs through the same non-elevated operator identity until the chat closes or the status-strip robot is used to revoke it. The model cannot invoke the operator path directly, the UI shows the exact path or command, and each decision, grant, lapse, and revocation is logged. File-tool denial comes from the impersonated Windows token; shell denial classification remains a text heuristic. Inspect the operation before approving: this escape deliberately bypasses service-account ACL and firewall restrictions and is not a security boundary.

## The one native file Agent_b ships that it did not build

`WebView2Loader.dll` sits beside `Agent_b.exe` so the product can host its own window (item 2hc)
instead of borrowing one from Edge.

- **What it is.** Microsoft's WebView2 SDK loader. It finds the installed WebView2 runtime and
  hands back the environment factory; the browser itself is the separately-installed Evergreen
  runtime, not this file.
- **Why we ship it at all.** The runtime does **not** provide it. Measured on 2026-09-22: the
  runtime directory holds `EmbeddedBrowserWebView.dll` and `webview2_integration.dll` and no
  loader, which is why every WebView2 application on this machine carries its own copy (Office,
  OneDrive, Citrix). The only entry point the runtime exposes directly is named
  `CreateWebViewEnvironmentWithOptionsInternal`, and building the product's main window on a
  symbol Microsoft marks internal is not a trade worth making quietly.
- **Origin, pinned.** `scripts/webview2-loader.json` records the source package
  (`Microsoft.Web.WebView2`, its version and the nupkg's own SHA-256), the path inside it, the
  file's SHA-256, and the Authenticode subject, issuer and thumbprint.
- **Verified twice before it runs.** The release step refuses to build a candidate whose loader
  does not match the pin, and **the installer verifies both the SHA-256 and the Authenticode
  signature before copying it** and refuses the install otherwise. A DLL beside an executable is
  loaded ahead of anything on the search path, so it is the file an attacker would most want to
  replace.
- **Loaded from one place only.** `Agent_b.exe` loads it by absolute path from its own directory.
  It never calls `LoadLibrary` on a bare name, which would search the working directory and `PATH`
  and could pick up somebody else's loader.
- **Absent is an ordinary answer.** No loader, or no runtime, means host mode declines with a
  logged reason and the browser window is used. The product does not depend on this file to run.
- **What was refused, and why.** `github.com/jchv/go-webview2` embeds three copies of this DLL and
  maps one into executable memory with `VirtualAlloc`/`VirtualProtect`. That is reflective DLL
  loading: unreviewable native code inside a binary we sign, never presented to the OS loader and
  so never signature-checked, using the technique this repository already bans the command-line
  forms of (`internal/tools/shell_policy.go` refuses `regsvr32` and `rundll32` by name). The
  decision and its reasoning are in `NOTES.md`, 2026-09-22.

## Network exposure

Agent_b has no user authentication and ships with `listen` bound to loopback. Each launch generates an unguessable mutation token delivered through the same-origin state stream; every non-read request requires that token, cross-origin browser mutations are rejected, framing is denied, and a restrictive Content Security Policy is sent. The native frameless window's minimize, maximize and close actions use that same guarded loopback boundary and are unavailable when no native host exists. This is a browser/CSRF barrier, not authentication against another process running as the operator. Moving the listener off loopback exposes an endpoint that can run shell commands and requires a real TLS/authentication design.

A second installed window launch treats `agent_b-run.json` as untrusted addressing data: it requires an exact canonical application-root match, the same live PID incarnation, a loopback port, and `/api/state` reporting that PID before it signals the install-root-and-PID-scoped activation event. It never rewrites the live marker. This prevents a stale or forged marker from redirecting the launch to an unrelated process; it is not an identity boundary against another process already running as the operator.

When **Check for updates** is on (the default), the operator process makes one anonymous GET at startup and once per day to GitHub's latest-release API for `rkclayton/agent_b`. It sends no Agent_b state, identifier, credential, cookie, or model content. A newer release is only reported; it is never downloaded or installed on a schedule. Pressing **Update** downloads `release.json` and `Agent_b-setup.exe` from that same release over HTTPS, bounds both responses, requires the manifest's release and clean executable identities to agree, and verifies the setup's exact size and SHA-256 before writing its final name or launching it. A mismatch is named and the file is not run. GitHub HTTPS plus the release manifest's digest is the download trust path: the configured self-signed signing identity is local and is not a public publisher identity. The setup then uses the existing single operator-initiated UAC flow and install-time signing path. A release-host or DNS compromise that can also replace the manifest can therefore supply matching bytes; a publicly trusted release-signing certificate is the future stronger identity hook retained by the deployment scripts.

The `fetch_url` and `web_search` tools are the governed public-network paths. Both perform GET-only, cookie-free requests with no model-supplied headers, recheck every redirect and resolved address, deny loopback/private/link-local destinations unless the exact host is configured in `tools.fetch.allow_internal_hosts`, cap time and bytes, and label returned text as untrusted in both model context and the timeline. `web_search` uses the same client and returns only engine-provided result metadata; fetching page content remains `fetch_url`'s job. Their browser-shaped TLS ClientHello improves compatibility; it does not impersonate a signed-in browser or make fetched instructions trustworthy. DNS/IP validation and domain allowlists reduce SSRF exposure but are application guards, not a network sandbox; `tools.fetch.allow_domains` is empty for first-run usability, but an explicit allowlist is recommended for untrusted workloads. With no allowlist, `tools.fetch.deny_domains` blocks known IP-geolocation hosts before DNS or request dispatch; an explicit allowlist supersedes this default guard. The system prompt separately forbids using network tools to discover the operator's location, identity, or IP. On a hardened Windows host, the service-account firewall blocks public network access from `shell`; these two tools run in the Agent_b process and are therefore the sanctioned service-context paths. Operator mode deliberately removes that firewall enforcement, and an unhardened host may let shell clients reach the network.

Each B chat may operate in its scratch/retained root and every repository named by the live plan list, and may read the plans tree. Each bound D chat writes only its immutable plan and may read its repository or any plan; operator identity cannot widen D write authority.

## Stored model content

`logs/*.jsonl` and retained `chats/*.jsonl` contain complete prompts and responses, including file contents and command output, and are ignored for that reason. Operational logs may rotate; retained chat journals remain until the operator explicitly confirms deletion of that chat.

`memory/*.md` contains model-authored notes that are injected into future sessions' system prompts for the same workspace. The `remember` and `recall` tools deliberately run as the Agent_b application identity rather than through the service-account `FileIdentity` wrapper. This is a narrow exception: neither tool accepts a path, filename, workspace, or routing argument; the application derives the one reachable file from the operator-configured memory directory and the active session workspace. The model supplies only note content to `remember`, while `recall` is read-only. Operator mode does not widen either tool. Running these tools through the service identity would also conflict with the hardened installation's deliberate write denial on the memory directory.

Each chat retains one canonical scratch or legacy base directory; B file tools add every live plan repository to that application-level root set, including while impersonating the service account, and no folder-selection or binding decision widens it. Repository instruction discovery prefers `AGENT_B.md`, then `AGENTS.md`, then `CLAUDE.md` at each selected root and reads only the first present file; ancestor traversal is otherwise unchanged. That text is prompt content, never executable policy. A root `.agentb/policy.json` is honored only after the operator approves its exact SHA-256, which is stored under the operator-owned data/memory root rather than in the repository; model file tools refuse writes beneath `.agentb/` under the named repo-policy immutability rule. Repository policy may loosen listed session defaults, but it can never control this list: **operator mode, elevation, signing, allow_internal_hosts, services allowlist**. Windows ACLs and the service account remain the security boundary; the root selector is an ergonomic guard, not containment.

A note derived from untrusted content can persist across sessions. Review it—the settings sheet shows the content and `recall` returns the dated stored entries—and remove the note file manually if it should not be trusted or retained.

Fetched text is one such untrusted source. The envelope does not follow content into a later `remember` call automatically, so review durable notes derived from fetched material with the same care as the original page.

`INBOX.md` is a pull-only operator channel under the operator-owned data root. `STOP`, notes, `TASK:`, and bounded delays cannot grant identity. Approval answers are ignored unless **Allow approvals from the mailbox** is enabled; changing that setting through HTTP requires the same verified local-operator process check as the shell identity controls, and the default is off. When enabled, whoever can write the synced operator folder can answer a pending card and therefore grant the non-elevated operator identity within that card's existing scope. Folder access and sync-account security are consequently the boundary for mailbox answers; the 40-line / 4-KB cap and verb parser are input hygiene, not containment.
